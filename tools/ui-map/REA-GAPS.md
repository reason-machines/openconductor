## REA gaps and bugs hit while building this map

REA 6.7.0 (`rea-agents`), Linux cloud machine, Chromium 1.x headless. Each was hit in this run.

1. **No UI-structure model for a Tauri/React bundle.** `analyze-javascript-application` on the decoded frontend (evidence/frontend) yields modules, call sites and literals, but no component tree, route table, dialog/menu/toast inventory or settings schema, and its IPC summary is Electron-only (0 operations for Tauri `invoke`). The inventory here is a regex pass over the minified chunks (`tools/ui-map/extract_inventory.py`), not REA output.
2. **The application graph is budget-truncated.** The semantic graph stops at 100,000 nodes with 1,876 limitations ("Resource constraint during analyze_javascript_application"), mostly in the 11.6 MB `renderApp` chunk that holds every screen, so REA cannot answer "which component renders this string".
3. **`capture-browser-scenario` fails the whole scenario on one bad locator** and names no step: the result is `execution_failure` with an empty or `screenshot undefined` artifact. `capture_ref.mjs` works around it by retrying shorter action prefixes and records the first action that failed (`menu-repo-actions`: clicking `[aria-label='tide-web actions']` after a hover).
4. **No way to tell a redirect from a render.** A scenario that lands on a different route (the frontend redirects gated settings pages to `/settings/user/general`) is reported as a successful capture; only the final `url` artifact shows it. `build_map.py` compares it with the requested path and marks those references `redirected`.
5. **`compare-web-screenshots` returns only a changed-pixel count and ratio.** No region boxes, no per-element diff and no diff image, so it cannot attribute a difference to a panel or row; the side-by-side diff images are drawn outside REA (Pillow).
6. **No native capture for the reference on this machine.** `capture-native-ui-scenario` and `observe-native-ui` need the Mac with Screen Recording and Accessibility, so the reference is the extracted frontend in Chromium, not Conductor's WKWebView window; native chrome (traffic lights, vibrancy, menus bar) is not measured.
7. **No WebKitGTK/tauri-driver capture tool.** REA cannot drive a Tauri app; the OpenConductor side uses WebDriver directly (tests/e2e), so its screenshots carry no REA Evidence id, only sha256.
8. **`--schema` for `capture-browser-scenario` still shows only `inputJson: string`**, so the accessibility and DOM capture options were found by trial (`capture.at_end: ["screenshot","url","dom","accessibility"]`).
9. **Role locators accept only 14 roles** (REA 6.8.0): `{kind: "role", role: "treeitem"}` is rejected as `invalid_value`, so tree rows (the right panel's All files tree) need a CSS locator.
10. **No `hover` action** in 6.8.0's `capture-browser-scenario` contract (`goto, click, fill, press, select_option, check, uncheck, wait_for, request, wait_for_timeout`); a hover step is rejected as invalid input (`invalid_request` at `actions[n].action`), which `capture_ref.mjs` then reported as `screenshot undefined`. There is no scroll action either: the lower half of the repository Misc page (`settings-repo-misc-lower`) is reached by clicking the Files to copy preview note, which Playwright scrolls into view first.
11. **A Chromium launch crash is reported as a bare `execution_failure`.** With a long `TMPDIR` Chromium aborts on "Socket path too long" for its singleton socket; REA only says "run `rea doctor`" with `cleanup_incomplete`. Set `TMPDIR` to a short path (for example `/tmp/t`).
12. **A `wait_for` whose text locator matches two elements fails the scenario as "screenshot missing".** On the repository Misc page `text=tide-web` matches the nav item and the root path, Playwright's strict mode rejects it, and REA reports only a missing screenshot (no step id, no "strict mode violation"). The Misc state now waits on the page description instead.
13. **No network-request view of the scenario.** REA records console and page errors but not the page's requests or the Tauri IPC behind them, so the cause of the repository-settings redirect (a failed `GET /organizations` inside Conductor's user service) was found by patching the bundle in Playwright and logging store writes, not with REA.
14. **No layout or geometry capture.** `capture-browser-scenario` returns screenshot, url, DOM and accessibility, but no element boxes (no `getBoundingClientRect`, computed styles or text line boxes) and has no evaluate action, so the sidebar alignment sweep (`tools/sidebar-screens/measure-alignment.mjs`) measures both apps with playwright-core directly; its numbers carry no REA Evidence id. The DOM artifact has no geometry either.
15. **REA's click and Playwright's click disagree on Conductor's repo header.** Through REA, `click` on `text=tide-web` expands the repo; the same locator clicked in playwright-core 1.64 (same Chromium, viewport, reduced motion and blocked service workers) does nothing, because the header is a @hello-pangea/dnd drag handle that swallows the pointer sequence. A dispatched DOM `click` expands it. REA does not record which input path its click used, so the difference cannot be explained from the Evidence.
16. **Hover states don't render in Conductor's headless capture, and REA has no hover action to force them.** Conductor gates its row hover controls on `@media (hover:hover)` group-hover, which headless Chromium doesn't match, so the repo row's "..." button stays at opacity 0 in every capture. `capture-browser-scenario` (REA 6.7.0) has no hover action and no way to emulate the `hover` media feature: its action kinds are `goto`, `click`, `fill`, `press`, `select_option`, `check`, `uncheck` and `wait_for_timeout`, and the string `hover` doesn't appear in `rea-agents/dist/mcp/browserScenario-BRUz7yN0.js` or its contract, so it can't capture the hovered row either. The alignment sweep therefore places Conductor's "..." from the DOM structure (`getBoundingClientRect` via playwright-core: 24×24 at x=189, y=219, the same as ours) rather than from a screenshot, and Conductor's side of the hover crops shows the row unhovered.

17. **`rea search` refuses an extracted JavaScript chunk** (REA 6.8.0, Settings UI pass). `rea search .rea-work/dist/assets/renderApp-D_fmY7hW.js "Opens settings in your browser"` fails with `capability_unavailable` / `unsupported_provider`: string search only routes to the native providers (`ghidra`, `hopper`, `ida`, `kuna`), none of which accepts a JS file, and there is no JS-aware fallback. The Settings tooltip and context-menu strings were located by reading the decoded chunk directly, then confirmed by rendering Conductor's own components in the harness.
18. **No hover in `capture-browser-scenario`, so tooltips can't be captured through REA** (still true in 6.8.0; see 10 and 16). `click` accepts `button: "right"` (the contract enum is `left|right`), so right-click menus can be, but a tooltip that opens on pointer-enter cannot. The Settings Back tooltip ("Esc", 100 ms) was measured with playwright-core, which carries no REA Evidence id.
19. **Real pointer input to Conductor's extracted frontend is dropped unless the pointer moves while the page loads** (harness/Playwright, not REA, recorded because it shapes the evidence). With playwright-core 1.64.1 and Chrome for Testing 155 headless, a page whose first mouse event arrives after Conductor has finished loading never gets `:hover`, pointer events or clicks (`document.querySelectorAll(":hover")` stays empty, window capture listeners see nothing), while the OpenConductor page in the same browser does. Moving the mouse 200 ms after `goto` keeps input working; the Settings measurements also dispatch `pointerenter`/`contextmenu` in-page so Conductor's own Base UI components render the result. The cause was not found.
20. **The menu inventory misses the sidebar's right-click menus.** `inventory.json` lists 15 `ContextMenuContent` popups (AFt, RFt, Svs, gwt, zOo, Lna, gJn, h0a, t9a, …), but the sidebar's workspace row (`Qj` -> `D9e`/`Aao`), repository header (`Dra` -> `Nra`/`uBi`), section header (`Yia` -> `Qia`/`oBi`) and "My workspaces" header (`rBi` -> `_Wt`) open a Base UI `ContextMenu.Root` (`wI`) with the generic Menu popup (`g2`/`b2`/`m2`) and `Menu.Item` (`Pu`), so none of them is in the inventory; the only sidebar entries there are `gJn` (account row, "Copy user info") and `Lna` (organization row, "Copy organization info"), both internal-build only (`internal_settings_enabled`). Found by reading the 24 `jsxs(wI|kS,…)` call sites in the bundle, not with REA, which has no "menus attached to this element" query.
21. **A rejected action can hang `capture-browser-scenario`.** A shot with a `hover` step (no hover action, see above) did not come back with `invalid_input`: the run printed nothing for over ten minutes on a loaded 4-vCPU machine and was killed. Shots no longer use hover, so the Set status / Move to section submenus have no REA reference capture.
22. **No motion capture.** `capture-browser-scenario` takes one screenshot at the end of a scenario: no frame sequence, no fake clock and no way to pause or seek CSS transitions, WAAPI or framer-motion animations, so it cannot show or time a transition. The sidebar motion frames (`tools/sidebar-screens/motion.mjs`, parity/side-by-side/sidebar/motion/) use Playwright's clock plus `document.getAnimations()` seeking instead, and the durations and easings come from reading the decoded chunk, not from REA.
23. **No computed-style or animation readout.** REA's DOM/accessibility capture has no `getComputedStyle`, so values such as Conductor's ghost-button press (`scale: 0.97`, `transform, translate, scale, rotate 0.15s cubic-bezier(0, 0, 0.2, 1)`) were read with `page.evaluate` in Playwright.
24. **Synthetic input reaches Conductor's renderer only through REA's own clicks.** In the tools/screens harness, Playwright CDP mouse/keyboard input (`page.click`, `page.mouse`) never arrives at Conductor's `document` (no pointerdown/mousedown/click events), while REA's `click` action works; motion.mjs dispatches DOM events in the page for both apps. Cause not found; recorded so the next capture lane does not assume CDP input works there.

Harness limits that shape the reference (not REA bugs): settings pages behind an organization or feature flag (`ports`, `key-bindings`, `terminal`, `internal`, `organization/*`, `cloud/setup`) redirect to General; `/dashboard` redirects to `/`. The `repos/$repoId/*` pages used to redirect too: Conductor's repository guard (`fHi`) sends any organization *error* to General, and the mock refused every network call. The mock now answers `POST /auth/exchange` and `GET /organizations` (an empty list, a local-only account) from `HTTP_FIXTURES` in `tools/screens/tauri-mock.js`, over the same `plugin:http` channel protocol Conductor reads, so those five pages render.

### Hit while building the repository Environment page (PR #484)

14. **`rea search` cannot read an extracted JavaScript bundle.** `rea search dist/assets/renderApp-D_fmY7hW.js "passed to agents"` fails with `capability_unavailable` / `unsupported_provider`: every string-search provider (ghidra, hopper, ida, kuna) is a native disassembler, so a minified `.js` file has no search route. The component (`zda`) and its helpers were located by reading the extracted chunk directly.
15. **`analyze-javascript-application` keeps only module nodes for the 11.6 MB `renderApp` chunk.** With `--source-path assets/renderApp-D_fmY7hW.js --max-heap-mb 4096 --max-semantic-nodes 400000` (2 m 36 s), the semantic graph holds 1,897 nodes, all `kind: module`, and 22,764 unknowns; no literal, function or call node holds "No variables set" or "Add environment variable", so REA cannot say which function renders the page. Coverage reports `partial` / `truncated` against the worker heap and 300 s timeout.
16. **No cross-chunk import resolution.** The paste parser the add sheet calls is `lPt` in `renderApp`, an import (`pl as lPt`) of `Q$e` from `index-BGEQ8YjU.js`; `index` also has an unrelated local `lPt` (a gzip helper). REA gives no export/import map between chunks, so the name had to be resolved by hand from the `export{…}` list; a name search alone points at the wrong function.
17. **No way to reach a Mac-only artifact from the Linux machine.** Conductor's binary was copied from Sven's Mac with Reason's device copy (`devices_copy_to_cloud`, sha256 `0ba55751…`), then decoded with `tools/extract_tauri_assets.py`; REA has no remote-artifact input.

### Hit while wiring the plan, question and Codex consent attention triggers (parity.sidebar.ws-unread)

25. **`rea search` on an extracted JavaScript chunk now fails as `target_kind_unsupported` from Kuna** (REA 6.8.0, `TMPDIR=/tmp/t npx rea search index-BGEQ8YjU.js "await _p("`). Earlier passes (17 above) saw `capability_unavailable` / `unsupported_provider`; this run routes the file to Kuna, which answers "Kuna decompiles executable images, not databases or archives." with `target_format: javascript`, so REA still has no string-search route for Conductor's frontend. The `_p` call sites (`index-BGEQ8YjU.js` sha256 `b5b01f33…`: `_p` @2,941,190; ExitPlanMode `needs_plan_response` @2,945,001; AskUserQuestion `needs_user_input` @2,945,451; Codex MCP elicitation @2,946,028; Codex permission approval @2,946,583; tool approval @2,947,277) were read as plain text by byte offset.
