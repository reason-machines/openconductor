# Title-bar drag region (reason/title-drag-region)

[title-drag-region--workspace--light.png](title-drag-region--workspace--light.png): Conductor 0.87.6 on the left
(`evidence/screens/chat--transcript-collapsed-tools--light.png`, REA capture of its embedded frontend, 1440x900),
OpenConductor on the right (this branch rebased on main, debug build of the Tauri app on Linux/WebKitGTK, window client area
1440x900). The drag change has no visible effect; the pair shows which strips drag: the sidebar header
(toggle row, back/forward, account, Home/Create/Search) and the workspace header row.

## What changed

- `core:default` does not include `core:window:allow-start-dragging` (tauri 2.12.5
  `permissions/window/autogenerated/reference.md`), so every `data-tauri-drag-region` mousedown was refused
  by the ACL and nothing dragged. The main window capability now grants it.
- tauri 2.12.5 `drag.js`: a bare `data-tauri-drag-region` drags only when the pressed element is the marked
  element itself; `"deep"` drags from anywhere inside except clickable elements (buttons, links, inputs, labels,
  `role=button/menuitem/tab/option/...`, `tabindex`); `"false"` stops it. The sidebar header and the workspace
  header (also the archived one) are now `"deep"`. Menus and pickers rendered inline in those headers
  (account menu, Open in menu, PR menu, target-branch picker) carry `data-tauri-drag-region="false"`.

workspace (`ocproj/drag-test`) open. Each line: press at a client coordinate, xdotool moves the pointer with
the button held, release, read the window position with xwininfo

## Not compared

- No live macOS capture: `~/oc-native-refs/` is absent on the machine this ran on and Sven's Mac was not
  reachable from it, so the reference is the REA/Chromium capture above, without native traffic lights.
- Conductor's own drag-region values (bare vs `"deep"`) and its window capability were not re-read with REA
  for this change; `evidence/packaging/conductor-plugin-commands.json` excludes core plugins.
- Linux drag goes through GTK `begin_move_drag` + the window manager; macOS goes through `NSWindow
  performWindowDragWithEvent`. Same frontend rule and ACL check, different native path; the macOS drag
  itself is unverified.
