# Packaging evidence

What OpenConductor's macOS bundle must look like, and how we know.

| File | What it is |
|---|---|
| `conductor-reference.json` | Info.plist key names, value types and signed entitlements of Conductor 0.87.6, generated by `tools/packaging_ref.py` from REA's `inspect-plist` and `inspect-signature` records. Text values are reduced to their type and length; none of Conductor's wording is kept. CI regenerates it and fails on drift. |
| `divergences.json` | What we leave out, each with a kind, a reason and its evidence. `info_plist` and `entitlements` are empty: since the microphone prompt and audio-input entitlement were added, the bundle carries every Info.plist key and entitlement REA found in Conductor. `bundled_resources` covers the eight files of Conductor's `Resources/bin` we don't ship and `linked_libraries` the five system frameworks Conductor links and we don't: `replaced` (we do the job another way), `by_design` (Conductor-only telemetry or staff tooling), `link_only` (linked, but Conductor's own code never calls it) or `not_built` (a real gap). `tools/parity_check.py` still scores them as missing and shows the reason in the report. |
| `rea/search-strings-*.json` | REA `search` records behind those reasons: the skill and `bin/.internal` strings of `MacOS/conductor`, every string of `bin/.internal/agent-launcher`, and the skill handoff in `bin/.internal/conductor-runtime`. The runtime record is cut down by `tools/rea_trim_search.py`: REA returns the runtime's whole embedded JavaScript bundle as one 13 MB string, so the file keeps REA's record fields and 7 excerpts, and names the full record's sha256 (`dd644726…`, 27 MB). |
| `rea/macho-framework-use.json` | `tools/macho_framework_use.py` over REA `inspect-macho` of `MacOS/conductor`: for each of the six frameworks only Conductor linked, the symbols it imports from it and the symbols of that framework's objc2 binding crate. |
| `own-build-rea.json` | REA's `inspect-signature` and `inspect-plist` on our own Developer ID signed build, plus that build's bundle-check result. |

## Sources

Conductor side: REA 6.7.0 on a copy of `/Applications/Conductor.app` on sven m5 max. The invocations are the `inspect_signature` and `inspect_plist` rows in `evidence/rea/rea-invocations.tsv`; see `rea-test-report.md`.

Our side: the same REA commands on `src-tauri/target/debug/bundle/macos/OpenConductor.app`, built with `scripts/package-macos.sh` on the same Mac (2026-11-05).

## Results

- Developer ID signed debug build: `codesign --verify --deep --strict` passes; hardened runtime on; entitlements `allow-jit` and `allow-unsigned-executable-memory`, the same two Conductor has minus audio input.
- `tools/check_macos_bundle.py --signing developer-id`: 37/37. Before #58 it was 36/37, because we lacked the one-time-code autofill key Conductor sets.
- Ad-hoc signed build in CI (`package-macos.yml`, macos-latest): bundle check runs on every PR that touches packaging, and its report is uploaded as an artifact.
- Not done: notarization and stapling. They need an Apple ID app password and team ID stored as secrets.

## Findings from the Conductor binaries

- **Skill handoff.** `MacOS/conductor` resolves its `conductor-skill` resource ("Failed to resolve conductor-skill resource") and passes the path to the sidecar in `CONDUCTOR_INTERNAL_SKILL_PLUGIN_DIR`, next to `CONDUCTOR_INTERNAL_BIN_DIR`, `CONDUCTOR_AGENT_BINARIES_DIR` and `CONDUCTOR_ACP_PROVIDERS_DIR` (`rea/search-strings-main-skill.json`, 0x102afc487 and 0x102cc0c8f). OpenConductor has no sidecar, so `agent/claude_cli.rs` passes the same bundled resource to Claude Code with `--plugin-dir`.
- **What the sidecar does with it** (`rea/search-strings-runtime-skill.json`, the bundle string at 0x104588027):
  - It trims the variable and accepts the folder only if `skills/conductor/SKILL.md` exists there; otherwise it logs a `[conductorSkillRuntime]` warning and loads no skill. OpenConductor checks for `.claude-plugin/plugin.json` instead. The bundled plugin has both files, so the result is the same.
  - Claude: every Agent SDK query gets the folder as `plugins: [{ type: "local", path }]`: chat turns, the session metadata query and the context-usage query. That is the SDK form of `--plugin-dir`.
  - Codex: the thread's `developerInstructions` get one sentence naming the `SKILL.md` path and saying when to use it (Conductor setup, `conductor.json`, workspace scripts, files to copy, MCP, review workflows). OpenConductor's Codex app-server runner can send `developerInstructions` (`agent/codex_rpc.rs`) but is not wired into chat yet, so no Codex thread gets the skill.
  - A second plugin, `skills/computer-admin/SKILL.md` from `CONDUCTOR_INTERNAL_COMPUTER_ADMIN_SKILL_PLUGIN_DIR`, is added only when computer-admin tools are on (an organization's cloud-computer admin workspace). Conductor 0.87.6 ships no such resource locally. Not rebuilt.
- **System frameworks** (`rea/macho-framework-use.json`). Of the six frameworks Conductor linked and our build did not:
  - CloudKit, CoreData, CoreImage and CoreText are `link_only`: no imported symbol and no symbol of their objc2 crate. For comparison, WebKit, which Conductor does use, has 0 imports and 64 `objc2_web_kit` symbols, because objc2 looks Objective-C classes up by name at run time.
  - OSAKit comes from `tauri-plugin-updater`: Conductor contains `osakit::Script` (`new_from_source`, `compile`, `execute`) next to `tauri_plugin_updater`, and the updater 2.14.1 source runs `do shell script … with administrator privileges` through `osakit` when installing an update needs admin rights. Since #355 added the updater, our build links OSAKit too (`evidence/parity/rea/trace-dylib-resolution-openconductor-app.json`, CI run 42078522125 at `a013933`).
  - UserNotifications is a real gap. Conductor defines its own `ConductorNotificationCenterDelegate` class and uses `objc2-user-notifications` to request authorization, post notifications with a title, body and `userInfo`, and read a clicked notification's action and `userInfo`. OpenConductor posts notifications only through `tauri-plugin-notification`, which on macOS goes through `notify-rust` and `mac-notification-sys` and reports no clicks. What Conductor does when a notification is clicked is not established.
- **`bin/.internal` roles.** `logger` forwards app logs to Conductor's Honeycomb telemetry and `actions` runs only for Conductor's internal users (same record, 0x102afc487). `agent-launcher` is a native exec wrapper that disclaims macOS permission responsibility so privacy prompts name the agent (`rea/search-strings-agent-launcher.json`). The reasons we don't ship each are in `divergences.json`.

## REA gaps hit in packaging

1. `inspect-signature` on an `.app` directory inspects only the main executable. It does not report the bundle seal, sealed resources or nested code, and says that trust validation is not examined, so it cannot replace `codesign --verify --strict`. We run both.
2. `inspect-signature` reports the signing `timestamp` as a localized string with no time zone.
3. No REA operation covers notarization or Gatekeeper (`spctl --assess`, `stapler validate`), so release readiness needs plain Apple tools.
4. `inspect` with no disassembler configured gives `provider_unavailable` instead of a bundle summary; `inspect-artifact` plus `inspect-plist` cover it.
5. `rea search` on `conductor-runtime` fails with `provider_unavailable` unless `GHIDRA_INSTALL_DIR` and `JAVA_HOME` are set in the environment; the error does not name either variable.
6. With both set, `rea search --provider ghidra` on `conductor-runtime` (sha256 `5723ead4…`) fails with `provider_timeout` at a 3600000 ms startup deadline (`REA_GHIDRA_STARTUP_TIMEOUT_MS`): the run took 3656 s. A run with a 3-hour deadline succeeded; it started at 08:32 and wrote its record at 09:33 (Mac local time), so Ghidra needs just over an hour of auto-analysis on this 76 MB binary before it answers a plain string search. REA serves no operation until auto-analysis is complete (the record's own limitation), and it has no analysis-free string scan for Mach-O.
7. `rea inspect-binary-layout` on Conductor's arm64 Mach-O main executable fails with `capability_unavailable`: the operation routes to the `pwntools-elf` provider, which supports only Linux x64 ELF. The per-library view exists in a different operation: `rea inspect-macho` lists `LC_LOAD_DYLIB` dependencies and imports with their source library (`imports.exhaustive` is false: "dyld_info textual imports may omit chained or toolchain-unsupported metadata"). Nothing points from `inspect-binary-layout` to `inspect-macho`. A Ghidra `search --kind procedures` for the same symbols was started before this was found and stopped unfinished.
8. `rea search --format json` on the main binary (a 47-minute Ghidra run) wrote 88 Ghidra decompiler `WARN` lines to stdout after the JSON document, so the output is not valid JSON; `rea/search-strings-main-skill.json` keeps the first document only. The 18-second run on `agent-launcher` had no trailing lines.
9. A `search` match returns the whole defined string that contains it, with no offset of the match inside it. In `conductor-runtime` the embedded JavaScript bundle is one 13 MB string, so every hit returns the whole bundle (a 27 MB record for one regex). `tools/rea_trim_search.py` cuts the record down to windows around the matches.
