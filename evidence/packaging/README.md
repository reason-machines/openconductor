# Packaging evidence

What OpenConductor's macOS bundle must look like, and how we know.

| File | What it is |
|---|---|
| `conductor-reference.json` | Info.plist key names, value types and signed entitlements of Conductor 0.87.6, generated by `tools/packaging_ref.py` from REA's `inspect-plist` and `inspect-signature` records. Text values are reduced to their type and length; none of Conductor's wording is kept. CI regenerates it and fails on drift. |
| `divergences.json` | What we leave out, each with a kind, a reason and its evidence. `info_plist` and `entitlements` are empty: since the microphone prompt and audio-input entitlement were added, the bundle carries every Info.plist key and entitlement REA found in Conductor. `bundled_resources` covers the eight files of Conductor's `Resources/bin` we don't ship: `replaced` (we do the job another way), `by_design` (Conductor-only telemetry or staff tooling) or `not_built` (a real gap). `tools/parity_check.py` still scores them as missing and shows the reason in the report. |
| `rea/search-strings-*.json` | REA `search` records behind those reasons: the skill and `bin/.internal` strings of `MacOS/conductor`, and every string of `bin/.internal/agent-launcher`. |
| `own-build-rea.json` | REA's `inspect-signature` and `inspect-plist` on our own Developer ID signed build, plus that build's bundle-check result. |

## Sources

Conductor side: REA 6.7.0 on a copy of `/Applications/Conductor.app` on sven m5 max. The invocations are the `inspect_signature` and `inspect_plist` rows in `evidence/rea/rea-invocations.tsv`; see `rea-test-report.md`.

Our side: the same REA commands on `src-tauri/target/debug/bundle/macos/OpenConductor.app`, built with `scripts/package-macos.sh` on the same Mac (2026-11-05).

## Results

- Developer ID signed debug build: `codesign --verify --deep --strict` passes; hardened runtime on; entitlements `allow-jit` and `allow-unsigned-executable-memory`, the same two Conductor has minus audio input.
- `tools/check_macos_bundle.py --signing developer-id`: 37/37. Before #58 it was 36/37, because we lacked the one-time-code autofill key Conductor sets.
- Ad-hoc signed build in CI (`package-macos.yml`, macos-latest): bundle check runs on every PR that touches packaging, and its report is uploaded as an artifact.
- Not done: notarization and stapling. They need an Apple ID app password and team ID stored as secrets.

## Findings from the Conductor binaries

- **Skill handoff.** `MacOS/conductor` resolves its `conductor-skill` resource ("Failed to resolve conductor-skill resource") and passes the path to the sidecar in `CONDUCTOR_INTERNAL_SKILL_PLUGIN_DIR`, next to `CONDUCTOR_INTERNAL_BIN_DIR`, `CONDUCTOR_AGENT_BINARIES_DIR` and `CONDUCTOR_ACP_PROVIDERS_DIR` (`rea/search-strings-main-skill.json`, 0x102afc487 and 0x102cc0c8f). OpenConductor has no sidecar, so `agent/claude_cli.rs` passes the same bundled resource to Claude Code with `--plugin-dir`.
- **`bin/.internal` roles.** `logger` forwards app logs to Conductor's Honeycomb telemetry and `actions` runs only for Conductor's internal users (same record, 0x102afc487). `agent-launcher` is a native exec wrapper that disclaims macOS permission responsibility so privacy prompts name the agent (`rea/search-strings-agent-launcher.json`). The reasons we don't ship each are in `divergences.json`.

## REA gaps hit in packaging

1. `inspect-signature` on an `.app` directory inspects only the main executable. It does not report the bundle seal, sealed resources or nested code, and says that trust validation is not examined, so it cannot replace `codesign --verify --strict`. We run both.
2. `inspect-signature` reports the signing `timestamp` as a localized string with no time zone.
3. No REA operation covers notarization or Gatekeeper (`spctl --assess`, `stapler validate`), so release readiness needs plain Apple tools.
4. `inspect` with no disassembler configured gives `provider_unavailable` instead of a bundle summary; `inspect-artifact` plus `inspect-plist` cover it.
5. `rea search` on `conductor-runtime` fails with `provider_unavailable` unless `GHIDRA_INSTALL_DIR` and `JAVA_HOME` are set in the environment; the error does not name either variable.
6. With both set, `rea search --provider ghidra` on `conductor-runtime` (sha256 `5723ead4…`) still fails with `provider_timeout`: Ghidra did not finish importing and analyzing the binary within its 3600000 ms startup deadline (`REA_GHIDRA_STARTUP_TIMEOUT_MS`). A plain string search should not need full auto-analysis; the next try raises the deadline and disables expensive analyzers with `REA_GHIDRA_DISABLED_ANALYZERS`. How Conductor hands its skill to agents is now read from the main binary instead (see Findings).
7. `rea inspect-binary-layout` on Conductor's arm64 Mach-O main executable fails with `capability_unavailable`: the operation routes to the `pwntools-elf` provider, which supports only Linux x64 ELF. REA has no linked-layout or per-library import view for Mach-O, so the six system frameworks Conductor links and we don't (CloudKit, CoreData, CoreImage, CoreText, OSAKit, UserNotifications) are being traced through a Ghidra `search --kind procedures` for their imported symbols instead.
8. `rea search --format json` on the main binary (a 47-minute Ghidra run) wrote 88 Ghidra decompiler `WARN` lines to stdout after the JSON document, so the output is not valid JSON; `rea/search-strings-main-skill.json` keeps the first document only. The 18-second run on `agent-launcher` had no trailing lines.
