# Pull requests: reference behavior vs our implementation

Implementation: [`src-tauri/src/pr/`](../../src-tauri/src/pr/mod.rs) (serde + serde_json, shells out to `gh`).
Tests: `src-tauri/src/pr/*_tests.rs`, run with [`run-tests.sh`](run-tests.sh) (built with `--cfg pr_harness`, which leaves out `commands.rs`); the Tauri crate declares `pub mod pr;` and registers `pr::commands::*` in `lib.rs`, so CI's Tauri job builds the commands.

Commands (JS names camelCase args): `pr_lookup(repoPath, requests)`, `pr_git_state(workspacePath, targetBranch)`, `pr_header_state(inputs)`, `pr_create_prompt(request)`, `pr_merge(repoPath, number, method?)`, `pr_set_auto_merge(repoPath, number, enabled, method?)`, `pr_mark_ready`, `pr_edit(repoPath, number, title?, body?)`, `pr_retarget(repoPath, number, base)`, `pr_approve(repoPath, number, headOid)`, `pr_list_open(repoPath)`, `gh_issue_list_open(repoPath)`, `pr_check_log(repoPath, check)`, `pr_rerun_failed_checks(repoPath, detailsUrls)` (the last two in `checks_commands.rs`). CI runs it on Linux and macOS (rustfmt check, tests, clippy `-D warnings`).

## Deliberate differences

- Wire format to the frontend (camelCase fields): `PrLookup` is `{kind: "none"|"closed"|"found", info?}`, header actions are `{type: "ready_to_merge", ...}`, tones and workspace statuses are strings (`out_of_sync`, `in-review`). The viewer's latest review is `{commitOid}` rather than a nested option so "reviewed, commit unknown" survives JSON.
- The batch size is fixed at 5; the reference halves it adaptively when GraphQL cost or rate limits bite. Deployments and stack fields are not selected yet.
- `gh` is run as an argv list, never through a shell string, so titles, bodies and branch names need no escaping. GraphQL string variables use `-f` (raw) so `gh` never turns a branch or owner like `123`, `true` or `@file` into a number, boolean or file read; only the `{owner}` / `{repo}` placeholders use `-F`, the only form `gh` expands. Allowed merge methods are parsed from JSON by us instead of `--jq`.
- The create-PR message is our own wording. A draft request adds `--draft` to the `gh pr create` line; the reference only says a draft was requested. The reference's "keep the workspace while a stack still has open PRs" exception to archive-on-merge is not modelled (no stacks yet).
- The header returns an action plus the numbers its label needs (`HeaderAction`, `Tone`); label text is left to the UI and written by us. Stacked-PR states (stack needs a rebase, stack merge) and the non-GitHub local-git forge's synthesized merge state are not modelled yet.
- Timestamps are parsed by our own RFC 3339 parser (`checks::parse_timestamp_ms`) rather than the JS `Date.parse`; GitHub only sends `...Z` UTC timestamps, which both read the same.
- Unknown GitHub enum values (a new `mergeStateStatus`, permission or queue state) deserialize to `Unknown` / `Other` instead of failing the response; the reference's schema validation rejects the whole response.
- Check logs and re-run run `gh` argv-style without a shell (the reference builds `cd "<path>" && gh run rerun ...` strings and appends `2>&1`); stderr and stdout are both kept for the `BlobNotFound` check. The job JSON is parsed by us rather than with the reference's `--jq` filter; the annotations call keeps the reference's `--jq`.
- Archive on merge reads only the user setting `git.archive_on_merge`; the reference's per-repository override (`getSettingForRepo`) is not built, as repositories have no settings scope yet. Its success toast has no Open PR / Unarchive buttons (there is no unarchive command), and the stacked-PR exception is not modelled. Every workspace is local, so the cloud-host skip never applies.
- The reference shows a failing Actions job's log in a PR view it navigates to; ours expands the log under the check row in the Checks tab. "Fix errors" sits beside Re-run in the Checks tab and sends to the workspace's own chat, switching to it; the instruction wording is ours. The header's "Fix errors" button (renderApp @ ~2,279,400, `git.fixErrors` shortcut) is not built.
- Create-from lists (`list`): the reference calls the GitHub REST API with its own OAuth token; we run `gh pr list` / `gh issue list --state open --limit 100 --json ...` in the checkout (100 rather than 50, as the picker asked), sort newest-updated first like the reference, and tag failures `no_github:` (gh missing, exit 4, `gh auth login`, HTTP 401) or `no_remote:` (no remotes, no GitHub-host remote, not a git repository) using gh 2.23's wording. Search-as-you-type over all open PRs/issues and by-number lookup (the reference's `search/issues` and `pulls/{n}` calls) are not built.

Differences: the upstream counts as diverged when it is both ahead and behind (our rule; the reference's sync check was not located). The reference sets `isMerged` optimistically while merging; we disable the button and re-read the PR. `automerge_enabled` and `treat_optional_checks_as_blocking` are user settings outside Conductor's settings file (index @ ~278,700); we read them as top-level keys of ours, and their Settings › Git rows come with the archive-on-merge work. There is no merge-method menu: the reference merges with the repository's allowed method and only names it in the tooltip, and so do we. The reference's `git.createPR` shortcut checks only that the forge can create PRs; ours also requires the header to be offering Create PR, so the shortcut cannot ask the agent for a second PR. Commit-and-push, pull, push and fix-checks states show as status chips that open the PR rather than running the action.

- `rea analyze-javascript-application` on a folder holding only `index-BGEQ8YjU.js`: exit 0 in 214 s, Evidence `ev_ed84d75ccb95a40cc1e33f548754ea751c7b2923f173806870054005b3164fd5` (59 MB; 1,381 modules, 65 endpoints, 15 storage nodes). ## PR title, description and base branch (pr_edit, pr_retarget)

Reference (Conductor v0.87.6 decoded frontend chunks, read by text search as data; offsets recorded by Session a4cdd6eb): `updatePrMetadata` (index ~721,160) trims the title, refuses an empty one ("PR title cannot be empty"), does nothing when neither field is given, then runs `gh pr edit <n> [--title] [--body]`, updates the cached PR info optimistically and refreshes. A failed edit shows "Failed to update PR on GitHub: <msg>", with a separate message when the error names the read:org scope (~3,167,200). `updatePrBase` (~722,230) runs `gh pr edit <n> --base <b>` ("Failed to change the PR's base branch") and is called from the workspace target-branch change only for an open, unmerged PR whose base differs (~3,321,350). UI (renderApp): the PR tab header's clickable title opens an "Edit PR title" dialog with Cancel / Save ("Saving..."), Enter saves and Save is disabled when empty (~9,660,300); the description is click-to-edit with placeholder "PR description" (~9,668,100); the target branch picker reads "Select target branch...", "Loading branches...", "Couldn't load branches." / Try again, "No branch found." and marks the default branch (~2,934,300).

Ours: `src/features/pr/edit/` (`edit.ts` rules + tests, `api.ts`, `PrHeader.tsx`), shown at the top of the Checks tab.

Differences:
- The header sits in the Checks tab; Conductor has a separate PR tab.
- The base-branch picker lives in the PR header and retargets only the PR. OpenConductor has no per-workspace target branch yet (it diffs against the repository default), so `intended_target_branch` is not saved and Graphite stacks are not checked.
- Errors show inline under the header rather than as toasts, and the saved title is not written to `workspaces.pr_title` directly; the refreshed lookup updates it through WorkspaceView's `onLookup`.
