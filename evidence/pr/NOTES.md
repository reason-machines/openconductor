# Pull requests: reference behavior vs our implementation

Implementation: [`src-tauri/src/pr/`](../../src-tauri/src/pr/mod.rs) (serde + serde_json, shells out to `gh`).
Tests: `src-tauri/src/pr/*_tests.rs`, run with [`run-tests.sh`](run-tests.sh) (built with `--cfg pr_harness`, which leaves out `commands.rs`); the Tauri crate declares `pub mod pr;` and registers `pr::commands::*` in `lib.rs`, so CI's Tauri job builds the commands.

Commands (JS names camelCase args): `pr_lookup(repoPath, requests)`, `pr_git_state(workspacePath, targetBranch)`, `pr_header_state(inputs)`, `pr_create_prompt(request)`, `pr_merge(repoPath, number, method?)`, `pr_set_auto_merge(repoPath, number, enabled, method?)`, `pr_mark_ready`, `pr_edit(repoPath, number, title?, body?)`, `pr_retarget(repoPath, number, base)`, `pr_approve(repoPath, number, headOid)`, `pr_list_open(repoPath)`, `gh_issue_list_open(repoPath)`, `pr_check_log(repoPath, check)`, `pr_rerun_failed_checks(repoPath, detailsUrls)` (the last two in `checks_commands.rs`). CI runs it on Linux and macOS (rustfmt check, tests, clippy `-D warnings`).

## Deliberate differences

- Wire format to the frontend (camelCase fields): `PrLookup` is `{kind: "none"|"closed"|"found", info?}`, header actions are `{type: "ready_to_merge", ...}`, tones and workspace statuses are strings (`out_of_sync`, `in-review`). The viewer's latest review is `{commitOid}` rather than a nested option so "reviewed, commit unknown" survives JSON.
- The batch size is fixed at 5; the reference halves it adaptively when GraphQL cost or rate limits bite. Deployments and stack fields are not selected yet.
- `gh` is run as an argv list, never through a shell string, so titles, bodies and branch names need no escaping. GraphQL string variables use `-f` (raw) so `gh` never turns a branch or owner like `123`, `true` or `@file` into a number, boolean or file read; only the `{owner}` / `{repo}` placeholders use `-F`, the only form `gh` expands. Allowed merge methods are parsed from JSON by us instead of `--jq`.
- The create-PR message is our own wording. A draft request adds `--draft` to the `gh pr create` line; the reference only says a draft was requested. The reference's "keep the workspace while a stack still has open PRs" exception to archive-on-merge is not modelled (no stacks yet).
- The header returns an action plus the numbers its label needs (`HeaderAction`, `Tone`); label text is left to the UI and written by us. Stacked-PR states (stack needs a rebase, stack merge) and the non-GitHub local-git forge's synthesized merge state are not modelled yet.
- Timestamps are parsed by our own RFC 3339 parser (`checks::parse_timestamp_ms`) rather than the JS `Date.parse`; GitHub only sends `...Z` UTC timestamps, which both read the same.
- Unknown GitHub enum values (a new `mergeStateStatus`, permission or queue state) deserialize to `Unknown` / `Other` instead of failing the response; the reference's schema validation rejects the whole response.
- Check logs and re-run run `gh` argv-style without a shell (the reference builds `cd "<path>" && gh run rerun ...` strings and appends `2>&1`); stderr and stdout are both kept for the `BlobNotFound` check. The job JSON is parsed by us rather than with the reference's `--jq` filter; the annotations call keeps the reference's `--jq`.
- Archive on merge covers every workspace, as in the reference, whose PR service runs `gGe` on every fetched PR (index @ ~768,300), not only the open one. The open workspace reports through its own lookup; `useArchiveOnMergeWatcher` (mounted in App) looks up every other live workspace with a worktree, per repository in one `pr_lookup` batch, every 60 s. Both feed one tracker (`observeLookup`), so a merge is acted on once. The polling interval is ours; the reference's scheduler interval was not read.
- The setting is read per repository, as `getSettingForRepo("archive_on_merge")` does (`archive_on_merge` is `xe({fileKey:"git.archive_on_merge"})`, workspace-configurable by default, index @ ~287,378 and ~293,233): `repo_archive_on_merge` returns `[git] archive_on_merge` from the highest repository layer (`.conductor/settings*.{toml,json}` shared, local, managed), and the user setting applies when none sets it. The `~/.conductor` user layer is skipped because our user setting lives in OpenConductor's own settings file.
- The success toast has Open PR and Unarchive (`toastSuccess(..., { action: { label: "Open PR" }, secondaryAction: { label: "Unarchive" } })`). Unarchive puts the workspace back in the sidebar and sets its row to `ready` (`db_unarchive_workspace`); the reference's unarchive also recreates the worktree and reruns setup, which ours does not need because our archive keeps the worktree.
- Not built: a full archive (archive script, worktree removal, `archive_commit`, branch deletion). Archive on merge uses the same archive as the Archive button, which so far only marks the row archived. The stacked-PR exception ("Workspace kept for the rest of the stack") is not modelled because there are no stacks yet, and the "workspace might be corrupted" error for a missing directory is not distinguished.
- The reference shows a failing Actions job's log in a PR view it navigates to; ours expands the log under the check row in the Checks tab. "Fix errors" sits beside Re-run in the Checks tab and sends to the workspace's own chat, switching to it; the instruction wording is ours. The `git.fixErrors` shortcut (Cmd+Shift+X) runs the same Fix errors when a failing check has a details URL and no fix is in flight (renderApp @ ~2,299,938: `failingStatusCheckRollups.some(Gds)`, `Gds` = `t => t.detailsUrl`, and `!isFixingChecks`); the button and the shortcut share one in-flight flag (`useFixErrors`). Ours also skips an archived workspace, where the button is disabled. The header's "Fix errors" button (renderApp @ ~2,279,028) is not built.
- Create-from lists (`list`): the reference calls the GitHub REST API with its own OAuth token; we run `gh pr list` / `gh issue list --state open --limit 100 --json ...` in the checkout (100 rather than 50, as the picker asked), sort newest-updated first like the reference, and tag failures `no_github:` (gh missing, exit 4, `gh auth login`, HTTP 401) or `no_remote:` (no remotes, no GitHub-host remote, not a git repository) using gh 2.23's wording. Search-as-you-type over all open PRs/issues and by-number lookup (the reference's `search/issues` and `pulls/{n}` calls) are not built.
