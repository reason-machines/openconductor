## Same-build reference producer, caller, and request consumer

1. Renderer `eSa` passes an `onResize` callback to `w9e`: `qc.resize(aVe(surfaceId), cols, rows)`. Its retained imports bind `qc` to index export `gh`, which exports `ts`; `ts=DAt()` returns the `$kt` runtime. Renderer `aVe` imports index export `g$`, which exports runtime-ID selector `bI`. This is a binding chain within the retained assets, not inference from symbol names.
2. `w9e` passes that callback through `dno`. `dno` runs `$At` during initial attachment and subsequent ResizeObserver/animation-frame fits. `$At` fits the actual terminal, compares measured columns/rows, and calls the provided callback with the terminal's current dimensions. Its complete retained body also handles a changed callback at already measured dimensions.
3. `$kt.resize(sessionId,cols,rows)` resolves the controller and invokes `V9.resize`. That method first updates its replay/screen dimensions, then calls `backendSession?.resize`. Thus dimensions can change while creation is still pending even when no backend object exists yet.
4. `V9.spawnBackendSession` snapshots screen dimensions into the launch request before awaiting backend creation. Once the returned backend is installed and its `whenReady` resolves, it rejects disposed, replaced, and exited cases. It then reads current screen dimensions and calls `s.resize(currentCols,currentRows)` **if either differs from the launch request**. This is the relevant post-startup reconciliation; it is not a new native-wrapper claim.
5. `DAt` defaults to `FAt`, whose local path is `_St` (the cloud path is not part of this unit). `_St.createSession` constructs `ySt`, awaits `i.spawn`, and returns it. `ySt.spawn` installs listeners, submits `pty_spawn`, and resolves readiness either from the matching ready event or as a fallback after successful invocation. Its complete `resize` method checks `isAlive`, then submits `pty_resize` with `{args:{id:ptyId,cols,rows}}`. Exit sets `isAlive=false`. These are frontend request and lifetime conditions only; Conductor's native body and kernel result are not inferred.

All listed complete bodies and the import/export bindings are retained under [source/spans](source/spans). No new whole-module parser was run. Earlier acquisition limitations (whole-module parser timeout, semantic-renderer memory exhaustion, unavailable REA MCP operation) are historical; retained exact bytes suffice for this bounded trace, not for native acceptance.

## OpenConductor lifetime and reachable same-input case

At the checked main, `startTab` registers the live terminal, installs `term.onResize` forwarding directly to `ptyResize`, dispatches the new tab, and awaits `spawnTerminal`. `attachTab` may fit that terminal while the spawn promise remains pending. `spawnTerminal` passes its then-current dimensions to `ptySpawn` but has no corresponding post-success dimension comparison. The only forwarding callback catches resize rejection and does not retain it for replay.

The existing bridge maps `ptySpawn` to `invoke("pty_spawn",{args})` and `ptyResize` to `invoke("pty_resize",{id,cols,rows})`; no bridge or native contract change is proposed. `terminal_commands.rs:pty_spawn` awaits settings-environment work before entering manager registration. `PtyManager.spawn` builds the session at request dimensions, inserts it, emits Ready, and eventually returns. `PtyManager.resize` validates dimensions then calls `get(id)`; `get` returns `NotFound` before insertion. This source establishes a legitimate pre-registration rejection boundary. It does not prove a specific real-world schedule, delivered kernel resize, or native Conductor behavior.

A deterministic request-level counterexample uses the same inputs: start at 80 columns by 24 rows; leave spawn pending; fit to 120 by 40 before registration; let the early resize reject as not registered; complete spawn without another geometry change. The reference controller has retained 120 by 40 and issues that size after readiness. OpenConductor's frontend submits only the rejected early request and has no accepted post-registration request. The new fixture will execute the production session module with controlled external PTY/xterm/DOM boundaries and assert submitted post-registration requests. It does not execute the reference code or an actual xterm package.

## Candidate shape and checks

Fix Root Causes and Model the Domain shaped the proposal: retain each attempt's launch-dimension pair in its async closure, then compare it to the existing terminal's current dimensions once that exact spawn succeeds. Reuse the current live-map identity and tab lifecycle; add no global size cache, queue, or independent state flag. Do not alter ready/input/cursor/clear/history or script behavior. A closed or exited terminal must not submit a late reconciliation; a resize failure must not turn an otherwise successful spawn into `spawn_error`.

The source-only fixture covers changed columns, changed rows, both changed, unchanged size, several startup sizes, successful invocation with delayed ready-event consumption, close and exit during startup, rejected spawn and retry, and ordinary later resize with sibling isolation. Only the existing serialized executor may run the frozen baseline and candidate. Assertions will remain byte-identical between RED and GREEN. TypeScript/React are the existing runtime dependencies; xterm is type-only and its runtime boundary is isolated as in the accepted cursor fixture. No full-app typecheck is predicted from the scoped resolver.
