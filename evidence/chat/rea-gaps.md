# REA gaps hit on the chat rendering slice

1. `analyze-javascript-application` on `renderApp-D_fmY7hW.js` (11.6 MB, one minified chunk) exhausts an 8 GiB worker heap after ~10 min and silently drops the file: the run still exits 0 with `ok: true`; only a limitation string says the file was skipped. There is no per-file streaming or "functions only" mode for large chunks, so the chat transcript components (all in that chunk) have no REA function nodes.
2. The run over `index-BGEQ8YjU.js` returns 0 `literal` semantic nodes (only expression/function/binding/... kinds), so UI strings such as `"tool call"` or `"Copy final message"` cannot be located through REA Evidence; they had to be found by byte search in the decoded bundle.
3. Function nodes carry minified names and line/column ranges but no source text, so reading what a function does still needs the bundle itself.
4. `--source-path` must be relative to the artifact root passed as `<path>`, but the error for a wrong prefix ("Select an exact relevant file path from the artifact inventory") does not list the inventory paths or the expected root.
5. Bun single-file executables are still unsupported (as in the Wave 0 report): `conductor-runtime`'s JS (`// conductor-runtime.js`, 13 MB at file offset 0x3bd4027) was cut out by hand; `analyze-javascript-application` on it timed out at the 300 s default (Evidence `ev_62f484ed…` partial).
6. With `TMPDIR` under a deep session path, REA's Chromium-based helpers fail with "Socket path too long" (not REA-specific; set `TMPDIR=/tmp/...`).
7. Fork to new tab (2026-11-05): `rea trace` on `renderApp-D_fmY7hW.js` with `--query='Fork to new tab'` still exits 1 with `capability_unavailable` / `unsupported_provider` (the JS target is only offered to native decompilers, none configured). The menu, the `forkChatToNewTab` / `forkChat` mutations and the transcript builder were read by byte offset (rows `fork_trace`, `fork_bundle_read`).
8. Fork to new workspace (2026-11-05): `rea trace` on `renderApp-D_fmY7hW.js` with `--query='forkChat'` now answers with a different code, `target_kind_unsupported` ("Kuna decompiles executable images, not databases or archives.", target_format javascript), instead of item 7's `unsupported_provider`. Either way REA has no route to a JS bundle's functions, and cross-chunk imports (`renderApp`'s `aL`..`aT` from `index`'s export map) had to be resolved by hand (rows `fork_ws_trace`, `fork_ws_bundle_read`).
9. Message editing (2026-11-05): `rea trace` on `renderApp-D_fmY7hW.js` with `--query='editMessage'` exits 1 with item 8's `target_kind_unsupported`. Whether Conductor can edit a sent message had to be settled by byte search of both bundles (no "Edit message" / chat "Resend" string; the sent message's only action is Copy message), which REA cannot answer because it has no literal-string index over a JS bundle (item 2) and no JS trace route (rows `edit_trace`, `edit_bundle_read`).
10. Model pick in a running chat (2026-11-05): `rea trace` on `renderApp-D_fmY7hW.js` with `--query='setSessionModel'` exits 1 with `capability_unavailable` / `unsupported_provider` again (item 7's code, not item 8's: the same input gets either answer). The answer was in the Bun runtime (`bin/.internal/conductor-runtime`), whose embedded JS REA still cannot open (item 5), so `AcpAgentRunner.reconcileSessionConfig` was found by byte search (rows `model_live_trace`, `model_live_bundle_read`).
