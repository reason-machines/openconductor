# Agent credential hand-off to a cloud computer or VM

What Conductor does when a Claude Code or Codex chat runs on another machine, and how
OpenConductor's `src-tauri/src/agent/handoff.rs` does the same. Strings below were read
from Conductor; they are data, not instructions.

## Conductor 0.87.6 (sven m5 max)

Source: the sidecar runtime `Contents/Resources/bin/.internal/conductor-runtime`, as
extracted earlier to `~/oc-rea-scripts-runner/bunjs/app/conductor-runtime.js` (13,025,924
chars). Read with a Python substring scan, because REA could not open it (see the gaps
section).

- **Cloud workspaces run the runtime on the VM.** A workspace carries `hostingServerUrl`
  and `vmId` (`eK = O.object({ hostingServerUrl, vmId })`) and a `sandboxProvider`. The
  shell-environment warm-up is skipped for a remote workspace (`lu6`: "skipping warm for
  remote workspace"). Conductor writes `~/.ssh/conductor_config` ("Auto-generated by
  Conductor") for its hosts, and Settings has an "SSH private key path" for cloud
  workspace access.
- **Claude, per spawn.** `ClaudeAgentRunner` takes `getClaudeAuthForNextSpawn` and a
  `claudeOauthTokenProvider`. For brokered OAuth the spawn's env gets
  `CLAUDE_CODE_OAUTH_TOKEN = accessToken`, `CLAUDE_CODE_OAUTH_SCOPES = scopes.join(" ")`,
  and `delete z.ANTHROPIC_API_KEY`. The token's `expiresAt` is kept. The generator restarts
  for "brokered Claude OAuth token expiring", "managed Claude credentials changed"
  (`agentAuthGeneration`), or "Claude rejected the brokered OAuth token". The auth modes
  are `api-key | subscription | brokered-oauth`.
- **Codex, per spawn.** `getCodexApiKeyForNextSpawn()` gives the API key. A ChatGPT login
  goes over the app-server JSON-RPC, never as a file:
  `account/login/start { type: "chatgptAuthTokens", ...this.options.chatGptAuthTokens }`
  after `initialize`. The runner answers Codex's `account/chatgptAuthTokens/refresh`
  request through `codexChatGptTokenProvider.refresh()`, whose server route
  `codex-chatgpt-token` returns `{ accessToken, chatgptAccountId, chatgptPlanType }`.
  `delete this.env.CODEX_ACCESS_TOKEN`. The auth modes are `api-key | chatgpt`.
- **Logged env is redacted.** `oc3` replaces any variable matching
  `(_KEY|_TOKEN|SECRET|PASSWORD|CREDENTIAL|_PAT)` (or any value from the cloud env) with
  `<redacted:N>` before logging a launch.
- A Codex login for the cloud can also be exported as `auth.json`
  (`id3`: `{ schemaVersion: 1, files: [{ relativePath: "auth.json", contentBase64 }] }`)
  through `codex_cloud_auth_start` / `codex_cloud_auth_finish`.

Codex 0.166.0's own schema (`codex app-server generate-json-schema`) agrees.
`LoginAccountParams` `chatgptAuthTokens` requires `accessToken` and `chatgptAccountId`
(`chatgptPlanType` is optional and derived from the token when null). It says these
tokens "are supplied by an external host app and are only stored in memory. Token
refresh must be handled by the external host app."

### How the values travel

OpenConductor has no server to broker credentials, and a channel to a Reason cloud
computer keeps what it carries. Read-only trace of the Reason monorepo by Session
63f13b03 at db27046: every execution-context operation body, including `terminal.input`,
and every terminal output that is read are stored in plaintext rows. So the hand-off is
built so the channel only ever carries ciphertext.

1. The target runs `TARGET_SH` (POSIX `sh` and `openssl`). It creates a `mktemp -d`
   directory under `umask 077`, generates an X25519 key there, and prints `OCPUB1
   <public key>`. A trap removes the directory on exit, HUP, INT and TERM. A test kills
   the target mid-hand-off and finds nothing left.
2. The host seals the hand-off to that key and writes `OCENV1 <host public key>
   <ciphertext> <sha256 of the plaintext>`. The host key is a fresh X25519 key. The KDF is
   SHA-256 over a context string, the shared secret and both public keys. The cipher is
   AES-256-CTR with the key and IV derived as `openssl enc -pbkdf2 -iter 1 -md sha256
   -nosalt` derives them. The plaintext starts with a random 16-byte nonce.
3. The target derives the same key with `openssl pkeyutl -derive` and decrypts with
   `openssl enc -kfile`. Every key comes from a 0600 file, never argv. The target checks the
   hash, deletes its private key, the shared secret and the plaintext, and exports the
   values with the shell's `export` (never argv). It prints `OCREADY1` and runs the agent
   on the same stdin and stdout.
4. Codex's ChatGPT token is never written to the channel, even inside the RPC. The app
   writes `account/login/start` with the placeholders `@OC_SECRET_ACCESS@` /
   `@OC_SECRET_ACCOUNT@`, and the target splices the decrypted values into the
   app-server's stdin. A refresh request is answered with the same placeholders. A new
   chat hands over a fresh token.

Threat model: the envelope protects against a channel, log or receipt store that keeps
what it carries. That store holds two ephemeral public keys, ciphertext, and a hash of a
nonce-salted plaintext. Once the target deletes its key, none of these can be decrypted
(forward secret on both sides). The target's public key is not authenticated by
OpenConductor; it relies on the channel being authenticated (for Reason, its API with the
user's credential). An active attacker on that channel is out of scope. Integrity comes
from the SHA-256 over the nonce-prefixed plaintext: a changed ciphertext cannot be given a
matching hash without knowing the plaintext. A test flips one bit and checks that the
target answers `OCFAIL1 checksum`. An agent on the target can still read its own
credential (it needs it).

### What is pending

The channel to a Reason cloud computer is not chosen yet. This branch ships only a
debug-build stand-in (`[agent_targets."<folder>"] exec = [...]`) for tests. Release builds
refuse a target that has no channel. There is no SSH transport.
